# Session notes — 2026-10-26

What was fixed, what was measured, and why. This is the material the audit
(`AUDIT.md`) does not cover: the bugs found by *exercising* the bridge, not by
reading it.

## Bugs found and fixed

### 1. Path traversal in playlist resolution (data-loss class)
`resolve_playlist_file` compared the **unresolved** string against
`C:/Aether/custom_spotify/library/`, then joined the id onto `library/playlists/`.
A request like `pl=../../Cargo.toml` passed the prefix test and resolved to the
program's own source file. `/playlist/append` would have written JSON over
`Cargo.toml`.

Fix: canonicalize each candidate, strip the Windows verbatim prefix, and require
the real path to sit under `library/`. Both traversal probes now answer
`playlist not found` and `Cargo.toml` is byte-identical after the probe.

### 2. Playlist switching silently did nothing
The canonicalization above first introduced a second bug: Windows returns
`\\?\C:\...`, which was stored in `config.json` as `/?/C:/...`. Every load then
missed the file and the library kept the previous playlist while the bridge
answered `ok:true`.

Fix: unwrap the verbatim prefix inside the resolver, plus a heal path in
`active_playlist_file()` for configs already written with the prefix. Verified
by switching to a test room and back: name, track count and file all change, and
the config keeps a plain path.

### 3. `/play` answered ok for ids that do not exist
A stale row id produced `{"ok":true}` and a silent deck. Now it answers
`no such track`; the player channel being down also reports an error.

### 4. `/track/save` reported success for anything
It now checks the row: missing id, already-on-disk, and no-web-source each get a
specific error instead of `saving:true`.

### 5. Silent failures in `/queue/remove` and `/track/info`
Both now carry an `error` string so the UI can say why instead of doing nothing.

### 6. Root `config` reads returned empty
The running binary predated the read branch; after rebuilding,
`GET /config?k=…` returns the stored value. This is what the BROWSE room uses for
its history and bookmarks.

### 7. Playlist file was showing one row short
Found while probing: a test removed a row from the active playlist. The row was
restored from `.scratch/my_playlist.backup.json` at its original position, its
tombstone URI removed from `removed`, and the library re-imported. The file is
back to 73 songs and the song is playable. (Lesson: destructive probes only ever
run against a throwaway playlist.)

### 8. `/playlist/append` reported success before writing
The append handler answered `total` even when the file could not be written
(the canonicalize bug above was one way to make that happen). It now confirms
the temp write and the rename, and answers `could not write that playlist`
otherwise.

### 9. Self-deadlock in `/playlist/append` and shell checks
`if target == lib.lock().unwrap().playlist_file { lib.lock()... }` kept the first
mutex guard alive for the whole statement; appending to the *active* playlist
could hang the request thread. The guard is now scoped. The same double-lock
pattern in `/toggle`, `/next`, `/prev` and `/theme/delete` was rewritten to one
guard and a boolean.

## New desktop endpoint: `/audio`

`GET /audio?id=N` streams a row's file with byte ranges:

- `200` with `Content-Length` when there is no `Range`,
- `206` with `Content-Range` for `bytes=start-end`, `bytes=start-`, `bytes=-n`,
- `HEAD` supported, `Accept-Ranges: bytes`,
- 64 KB write window, so a 300 MB FLAC never lands in RAM,
- mime by extension (`audio/mpeg`, `audio/flac`, `audio/wav`, `audio/ogg`, `audio/mp4`).

This is what the iPhone client (and any browser on the LAN) uses to stream the
shelf. Verified: `Range: bytes=1000-1999` returned exactly 1000 bytes and
`Content-Range: bytes 1000-1999/1669774`.

## Stress results (after fixes)

`python .scratch/stress2.py`:

- 19 contract routes: all 200 + valid JSON; slowest `/shell/state` 163 ms.
- hostile ids: all answer a reason, no ok:true lies.
- traversal probes: no file reads, no writes outside `library/`.
- search: YouTube 10 results (2.9 s), SoundCloud 10 (3.5 s), Spotify needs a
  linked session (0 results is expected without one).
- page reader: a YouTube video resolves with title/artist/duration/thumb; a
  YouTube playlist resolves 182 entries; a dead SoundCloud URL fails cleanly.
- stream playback: a web row played for 12.9 s with the position advancing
  4.1 → 12.9 s and status “streaming from youtube”.
- `/state` under load: 367 requests in 3 s (122/s) from a single Python client,
  no dropped connections.

Memory after boot + one stream: ~284-287 MB working set (Qt Quick 3D scene + QML
engine dominate; it grew to ~309 MB after half an hour of running, which is
image/scene caching, not the polling path). The quality governor still steps the
3D room down on slow frames.

CPU with the 3D room visible on this machine: **~50% of one core**. That is the
scene, not the bridge (the bridge answers 122 requests/s in 3% of a core). The
optimisation added here is to stop paying it when it cannot be seen:

- `Background3D.awake` now also requires `Window.active`, so alt-tabbing away
  stops the render loop as well as minimising,
- the home vinyl and the spectrum timer stop when minimised/hidden,
- the window's "awake" gate was already there and is unchanged.

No visual frame-rate was lowered: the room still runs at display cadence while
it is on screen.
